## 3. 五大升级方向（逐条给出可验收标准）

### 方向一：UI 设计全面升级

**现状问题**：顶栏密度高（v1.20 才刚从 13 按钮收成 8）、三套反馈机制并存（`alert/confirm/prompt` + `status` 文本 + 无统一 toast）、小地图深色主题未适配（`drawMinimap` 硬编码 `#f4f6fb`/`#b45309`，见 HANDOVER L66）。

**要求**：
1. **建立设计令牌（Design Token）体系**：间距、圆角、字号、层级阴影、动画时长统一为 CSS 变量。
   浅色基础在 `index.html` 的 `:root`，深色覆盖在 `canvas_theme.css` 的 `html[data-theme="dark"]`。**新增 UI 必须双主题可用**。
2. **反馈机制统一**：实现全项目唯一的 toast 组件，替换散落的 `alert/confirm/prompt`。
   危险操作（删除章节/拒绝提案/覆盖文件）改用统一确认弹窗。**AGENTS.md 明确要求：若引入 toast，必须全项目统一实现。**
3. **信息密度与视觉层级**：重排顶栏与侧栏，让「当前项目 / 当前卷 / 当前章节 / 字数 / 保存状态」一眼可读。
4. **补完小地图等深色主题遗漏**，用 `var(--*)` 替换所有硬编码颜色。
5. **可访问性与动效**：键盘可达、焦点可见、`prefers-reduced-motion` 降级。

**验收**：亮/暗两套主题下逐屏截图目视核验；全项目 `grep` 硬编码色值归零（或仅剩 token 定义处）；无残留 `alert(`。

---

### 方向二：画布展示升级

**现状问题**：进度轴是唯一视图，节点多了会拥挤；连线的三种自动算法**同时叠加**，缺少"我现在在看什么关系"的表达力；无书签/视图记忆。

**要求**：
1. **分层过滤（Lane / 泳道）**：让作者按「角色线 / 伏笔线 / 势力线 / 感情线」独立查看剧情推进，而不是所有连线糊在一起。
   复用既有 `lane` 字段（L2 front matter 已支持）。
2. **连线语义化**：不同类型的连线（实体关联 / 标题匹配 / 章节聚焦 / 手动）要有**可区分的视觉语言**（颜色/线型/粗细），并可单独开关。
   已有主题变量 `--edge-auto` / `--edge-manual`（注意：`canvas_theme.css` 内有**更高优先级的深色覆盖**会遮蔽变量，改色必须同步改那两处——见 HANDOVER L66 的坑）。
3. **视图状态记忆**：缩放、平移、折叠、筛选、当前泳道，切项目/重启后恢复。
4. **大项目性能**：章节数上千时保持 60fps 拖拽。v1.18 已优化过一次拖拽掉帧，勿回归。
5. **聚焦模式**：「只看这一章周边 N 章」的局部放大视图，降低长篇认知负荷。

**验收**：`npm test` 新增泳道切换、连线分类开关、视图记忆的 `check(...)`；实测 1000+ 章节项目拖拽帧率。

---

### 方向三：小说数据统计 / 角色状态 / 伏笔等信息的**实时统一监控**

> **这是本次升级的核心，也是当前最大欠账。**

**现状问题（关键）**：数据是**散的**。
- 全书统计走 `/api/bookstats`（卷/大纲/伏笔回收率/分类），是**一次性快照**，关掉弹窗就没了。
- 角色状态在 `追踪/角色状态.md` 节点里，伏笔在 `追踪/伏笔.md` 节点里，只是被"扫进来当节点看"，**没有状态机**。
- 一致性审查产出 `auditStats`（最多 200 条），但**与画布、统计、AI 对话三者不联动**。
- 结果：作者要判断"这章有没有问题"，得分别开统计、开看板、开审查、再问 AI——**四个地方看同一件事**。

**要求：建立统一的「监控中心（Monitor Center）」**

1. **统一数据模型**：定义单一的 `ProjectHealth` 结构，聚合
   - 进度（总字数/章节数/卷/日均/更新时间线）
   - 角色状态（每个角色的当前状态、位置、关系、最后出场章节）
   - 伏笔状态（已埋 / 待回收 / 已回收 / **长期未回收告警** / 状态矛盾）
   - 设定一致性（12 维评分历史走势）
   - 大纲完成度、未识别节点数、断更风险
   **所有 UI（画布徽标、状态栏、分析面板、AI 上下文）都从这一份数据渲染**，禁止各视图各自算一遍。

2. **实时性**：文件变更后自动重算（复用 `node --watch` 或加文件监听），**实时**反映到状态栏徽标与画布节点角标。
   明确区分"实时"与"重计算成本"，大项目用增量更新而非全量重扫。

3. **可视化**：状态栏成为常驻的**迷你监控条**（字数 / 伏笔待收 / 一致性分 / 未保存），点击下钻到监控中心。

4. **告警驱动**：不是展示数字，而是给出**"需要你动手的事"**——
   "伏笔《XX》已埋 30 章未回收"、"角色 A 在第 40 章后消失 20 章"、"本章与设定冲突 2 处"。
   每条告警可直接跳转到对应章节/节点（统一走 `focusNode()`，见下）。

5. **AI 联动**：监控数据自动进入 AI 上下文封包，让 AI 回答基于**真实状态**而非摘要猜测。
   （既有封包机制在 `server.js` L1122 起，扩展它，不要另起一套。）

**硬性约束（来自 1.20 血的教训）**：
- **所有跳转统一走 `focusNode(id)`**，禁止再用 `showDetail()` 做跳转。
  原因：`focusNode` 会先清空搜索框——侧栏有搜索词时目标节点被 `applyFilters()` 过滤隐藏，用 `showDetail` 跳转**看起来完全像"按钮坏了"**。这条隐性依赖是 1.20 专门修复的回归点，必须加测试守住。
- 统计/监控的每个数字都要**可下钻到"待办明细"**，而不是全量清单（1.20 已确立此原则）。

**验收**：新增 `/api/health`（或等价）单一聚合接口；冒烟测试验证"监控数字 → 下钻明细 → 跳转节点"完整动线；验证修改章节文件后监控数字**实时**变化。

### 方向四：小说语句去 AI 味

**现状问题**：已有一个 `deslop` 人格和一个 `polish` 人格，规则写在**提示词字符串里**（`server.js` L2939、L2135），内容是：
> "删解释总结、删光滑排比和'不是…是…'套路、把'告诉情绪'改成动作短句"。

**这远远不够**。它是一次性重写，**没有检测、没有量化、没有针对性、没有学习作者本人文风**。

**要求：建立「AI 味检测 → 定位 → 针对性改写」闭环**

1. **量化检测引擎（规则 + 统计，可离线跑）**，输出 0~100 的「AI 味指数」与**逐句定位**。
   至少覆盖这些可判定的特征：
   - **句式**：排比堆砌、"不是A而是B"、"与其说…不如说"、三段式递进、每段等长。
   - **词汇**：高频抽象词（"仿佛/似乎/某种/一丝/一抹/不禁/缓缓/深深"）、四字词滥用、书面腔。
   - **情绪表达**：直述情绪（"他很愤怒"）而非动作/生理反应；形容词副词密度。
   - **结构**：每段"结论+解释"、结尾升华总结、对话后必跟心理解释。
   - **重复**：n-gram 自重复、同义词机械替换痕迹、段落开头/结尾句式同构。
   - **标点节奏**：逗号长句、破折号滥用、感叹号密度、句长方差过低（AI 句式过于均匀）。
   **每个特征必须给出可解释的命中位置和理由**，不能只给一个黑箱分数。

2. **作者文风指纹（Voiceprint）**：从作者**已认可的正文**中提取个人文风基线
   （句长分布、词汇偏好、对话占比、标点习惯、常用动词），
   检测时对比的是"偏离你自己的文风"，而不是"绝对标准"。**这是本方向最有价值的部分。**

3. **针对性改写**：只改命中的句子，保留剧情信息、人名地名、叙事视角与人称。
   **禁止整章重写**——那会引入新错误并丢失作者语感。改完给出 diff 供审阅（复用既有 proposal 机制）。

4. **接入写作流程**：在编辑器中实时标注 AI 味句子（波浪线 + 悬停理由），可一键改写或忽略。

**验收**：拿作者真实章节跑检测，输出定位报告；改写前后对比必须**保留全部剧情信息**；
新增冒烟测试覆盖检测接口与定位准确性。

**注意**：这是**检测与建议**能力，最终决定权永远在作者。不要做"自动重写全章"。

### 方向五：剧情创意

**现状问题**：AI 能"续写下一章"（`server.js` L1461）和"规划大纲"（`outline` 人格），
但都是**单轮生成**——没有基于全书状态的**创意提案系统**，也没有"避免重复套路"的机制。

**要求**：
1. **创意提案器**：基于当前 `ProjectHealth`（未回收伏笔、角色状态、已用桥段），
   给出**结构化**的剧情选项而非一段泛泛文字：
   - 每个提案含：触发点（用哪条伏笔/哪个角色状态）、冲突设计、预期爽点、风险、预计跨度（几章）。
   - **一次给 3~5 个方向不同的选项**，标注各自代价，让作者选。
2. **反套路约束**：记录本书**已用过的桥段/转折**，新提案须主动避开，并说明"与第 X 章的 Y 有何不同"。
3. **伏笔驱动的剧情规划**：优先建议**回收长期未回收伏笔**的剧情路径——直接消费方向三的监控数据。
4. **创意可执行化**：选中的提案能一键生成分章大纲提案（走既有 proposal 审阅流程写盘）。
5. **多方案权衡**：明确列出每个提案对节奏、角色弧光、伏笔回收率的影响。

**验收**：给定一个真实项目，产出 3~5 个结构化提案；验证提案确实引用了真实存在的伏笔/角色状态

## 4. 硬性约束（违反即返工）

**来自 AGENTS.md，逐条必须遵守：**

1. **不修改 `D:\小说` 下各小说项目的正文内容。** Markdown 是用户数据真源，只能通过 `server.js` 受控 API 读写。
2. **保持无框架原生 JS/CSS。** 不要引入 React/Vue/打包器/重型依赖。
3. **路径安全**：任何文件读写必须经 `projectDir()` / `resolveProjectRoot()` / `isSafePath()` 校验，禁止拼接用户可控路径。
4. **写文件先写 `.bak`**，沿用 `writeText()`。
5. **AI 写盘必须走 proposal**：先生成提案 → 用户审阅 → `/api/apply_proposal`，**禁止绕过直接写盘**。
6. **API 风格**：统一返回 `{ ok: true, ... }` 或 `{ error: "..." }`，不抛未处理异常。
7. **XSS**：动态插入用户内容必须 `escapeHtml()` 或 `textContent`。
8. **布局文件 `小说画布.json` 只存视图状态**，不存正文，保持 `version: 3`（若需升版，说明迁移方案）。
9. **不要用会改变布局的临时错误/警告块。**
10. **新增扫描规则写进项目 `novel-canvas.config.json`**，不要在代码里硬编码个人文件名。

**来自 CHANGELOG 1.20 的踩坑记录（务必避开）：**
- `.modal` 自带 `overflow-y: auto`；要覆盖必须用**双类** `.modal.analysisModal` 提特异性，否则单类被压过。
- 显隐**用 `.on` 类驱动，不要用 `hidden` 属性**（ID 级 `display: flex` 会压过 `[hidden]`）。
- `focusNode` 会清空搜索框，这是跳转正确性的隐性依赖，**别删**。
- `pruneBackups` 曾因在写请求路径上做上百次 `rmSync` 导致**写请求挂死**——已改为 `renameSync` 归档。
  **任何新的清理/批处理逻辑，都不许放在写请求的关键路径上。**
