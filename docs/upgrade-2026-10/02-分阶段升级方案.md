## 阶段 0：冒烟测试隔离（前置，排最前）

**验收**：

- `D:\小说\_nc_test_residue\` 残留目录**由用户确认后**再清理（本文档不代删）。

## 阶段 1：数据口径统一 + fmCache 修复（P0-a，核心中的核心）

**动机**：勘察已实锤三套口径分叉（卷归属/字数/未回收定义）+ fmCache 零失效。这是"监控中心"的地基——口径不统一，监控中心建得再漂亮也是在展示错误数据。

### 1.1 卷归属单口径（用户已拍板：**两种布局都要支持**，2026-10-04）
- **统一语义（一套代码，自动适配分卷/不分卷两种布局）**：
  - **分卷项目**：父目录含「卷」→ 用父目录名（兼容现有所有项目，`第一卷/`、`第三卷·源能回廊/` 等零迁移）；目录不含「卷」但同层存在多个章节子目录时，也按目录分组（修掉勘察 1.1 的"下钻 0 行"分叉场景）。
  - **不分卷项目**：章节平铺在项目根或单一目录 → 全部归入 `'未分卷'` 一组，统计/下钻/看板/泳道把它当作唯一的卷正常渲染（不报错、不出现空表）。
  - 标题正则提取（`第X卷`）仅作**兜底提示**，不作为分组依据（避免同一文件前后端各算各的）。
  - 弃用 `'全局'` 兜底词，统一为 `'未分卷'`；如需例外，项目可在 `novel-canvas.config.json` 里显式指定卷映射（走配置，不硬编码）。
- 实现：`server.js` 抽 `volumeKeyOfNode()` 为唯一实现并在 `buildNodes` 输出里带 `volume` 字段；前端 `app.js` **删除 L95 死代码、删除 L317 自算逻辑**，一律消费节点自带 `volume`。
- 同步修正 server.js L1907 的错误注释。

### 1.2 字数单口径
- 统一为 **不含空白**（与编辑器计数/网文作者习惯一致）：server `buildBookStats` L1904/1914 改 `replace(/\s+/g,'').length`。
- 统计弹窗「总字数」与看板「章节总字数」验收时**必须逐位相等**。

### 1.3 「未回收伏笔」定义统一
- 采用看板口径（`已埋 + 计划回收` 计未回收，`待回收`/`断线`/`未标记` 单列），server `buildBookStats` 的 `planted` 细分；两个视图同源渲染。

### 1.4 fmCache 失效
- 最小修复：`writeText()`（所有写盘必经收口）内调用 `invalidateFmCache(root)`；另在 `/api/file/delete`/`rename` 补调用。
- 可选加固：`fileFrontMatter` 缓存值带 `mtimeMs` 双保险（防止未来新增绕过 writeText 的写盘点）。

**验收**：
- 构造临时 fixture 项目：含 `第一卷/`、`不带卷字目录/`、根目录散装章节 → `/api/bookstats` 各卷数字 = 前端下钻行数之和；下钻 0 行的场景归零。
- 另造一个**完全不分卷**的 fixture 项目（章节全部平铺）→ 统计/下钻/看板均显示为单一 `未分卷` 组，无空表、无报错。
- 同一项目统计弹窗总字数 === 看板总字数 === 各章编辑器字数之和。
- 改某文件 front matter 的 `lane` → 保存 → `GET /api/data` 返回新 lane（无需改配置/重启）。
- 冒烟新增 3 条 check（卷口径一致、字数口径一致、fm 保存即生效）；既有用例零回归。

**涉及文件**：`server.js`、`app.js`、`scripts/smoke-test.js`。**不碰**：`index.html`、`canvas_theme.css`。
**风险点**：`buildNodes` 是全部 API 的数据源，加字段属增量（不动既有字段），低风险；字数口径变更会让统计数字"变小"，CHANGELOG 必须写明是口径修正而非丢字。

## 阶段 2：统一监控中心 ProjectHealth（P0-b，用户最痛）

**前置**：阶段 1 完成（口径统一）后才允许开始。

**设计**：
- `server.js` 新增 `/api/health` 单一聚合接口，返回 `ProjectHealth`：
  - 进度（总字数/章节/卷/近 7 日更新）——复用阶段 1 统一后的 `buildBookStats`
  - 角色状态（当前状态/最后出场章节）——扫 `追踪/角色状态.md` 节点（只读解析，不建状态机写回）
  - 伏笔（分状态计数 + **长期未回收告警**：已埋超过 N 章未回收，N 可配置进 `novel-canvas.config.json`）
  - 一致性评分（复用 `auditStats` 既有历史）
  - 未识别节点数、断更风险（最近章节 mtime）
- 前端：状态栏升级为**常驻迷你监控条**（字数 / 伏笔待收 / 一致性分 / 未保存），点击进入分析弹窗新「监控」标签（复用 v1.20 的 `analysisModal` 标签体系，**不开新弹窗**）。
- 告警列表每条 = 「需要你动手的事」+ `focusNode(id)` 跳转（**禁止 showDetail 跳转**，1.20 隐性依赖）。
- 每个数字可下钻到**待办明细**（非全量清单，1.20 已确立原则）。
- AI 联动：`buildConsistencyPackage`（server.js L1122 起）封包时附加 ProjectHealth 摘要（数百字符级，防膨胀），**不另起一套上下文机制**。

**实时性策略（明确分层，避免过度工程）**：
- 文件保存/提案应用后：服务端已天然重算（buildNodes 每次现扫）+ 阶段 1 的 fmCache 失效保证数据新鲜；
- 前端：监控条随 `loadData()` 刷新 + 60s 轮询兜底；
- **不引入** fs.watch 推送/WebSocket（无构建原生栈下成本高、收益边际），在方案中明示此为刻意取舍。

**验收**：
- 冒烟动线：「监控条数字 → 点击下钻到待办明细 → 点击条目 focusNode 跳转且画布高亮」全链路 check；
- 保存章节文件后 60s 内监控条字数变化（或 loadData 后立即变化）；
- 长期未回收伏笔告警出现在列表且跳转目标正确；
- AI 对话日志可见封包含 health 摘要（调试用例，非 LLM 断言）。

**涉及文件**：`server.js`、`app.js`、`index.html`（监控条 DOM + 一个 analysis 标签）、`scripts/smoke-test.js`。
**风险点**：`.modal.analysisModal` 双类特异性坑（1.20 已记录）；分析弹窗宽度需给新标签定档。

## 阶段 3：去 AI 味闭环（P1）

**设计**（本地规则引擎，**零 LLM 成本**起步）：
- `server.js` 新增 `/api/deslop/scan`：输入章节文本，输出「AI 味指数 0~100」+ **逐句命中清单**（特征类型、位置、理由）。特征集按任务书六类实现（句式/词汇/情绪/结构/重复/标点节奏），每条规则独立函数、可单测。
- **文风指纹**：`/api/deslop/voiceprint` 从项目已写章节提取基线（句长分布、对话占比、标点习惯、高频动词），落 `.data/voiceprint-<project>.json`；评分 = 偏离自身文风的程度。指纹可手动刷新。
- 编辑器内标注（波浪线 + 悬停理由），「一键改写」走**既有 proposal 机制**产出句级 diff，**禁止整章重写**；`deslop`/`polish` 人格提示词改为消费命中清单（只改命中句）。
- 参考工作区既有方法论：`D:\小说\.workbuddy\memory\MEMORY.md` 的「去 AI 味改稿方法论」（四种病灶、七条做法、铁律）直接转写为检测规则与改写约束——**这是作者本人验证过的标准，优先级高于通用规则**。

**验收**：
- 拿《房车求生》Ch1~3（已被作者人工改写过）跑检测：改写后版本指数应显著低于任意 AI 生成稿；**只读扫描，绝不写盘**。
- 命中清单每条含位置+理由（无黑箱分数）；改写提案经 proposal 审阅后写盘，剧情信息零丢失（关键数值/节点清单回查，沿用作者既有核验脚本思路）。
- 冒烟：检测接口结构 check + 一条已知 AI 味文本的命中断言。

**涉及文件**：`server.js`、`file_editor.js`（编辑器标注）、`app.js`、`scripts/smoke-test.js`。

## 阶段 4：剧情创意提案器（P1）

**设计**：
- 新 AI 人格/指令 `plot`：上下文封包 = ProjectHealth 摘要（阶段 2）+ 未回收伏笔清单 + 已用桥段记录。
- 输出**结构化**提案（JSON schema 校验）：触发点 / 冲突设计 / 预期爽点 / 风险 / 预计跨度，一次 3~5 个方向；schema 不合格直接报解析错误（复用 consistency/advance 的解析与错误风格）。
- 「已用桥段」记录：`.data/plot-devices-<project>.json`，提案被采纳时写入；新提案 prompt 要求其自述"与第 X 章 Y 的区别"。
- 选中提案 → 一键转**分章大纲提案**，走既有 `/api/apply_proposal` 审阅写盘。
- 硬约束沿用既有 AI 工具规则：提案中引用的伏笔/角色必须经 `read_node`/`search` 查证，不得编造。

**验收**：真实项目产出 3~5 个结构化提案，引用对象全部真实存在（抽查）；采纳后落盘走 proposal 流程；冒烟覆盖 schema 校验失败分支。

**涉及文件**：`server.js`、`app.js`、`scripts/smoke-test.js`。

## 全局纪律（每阶段都适用）

1. 提交流程：`node --check` 全量 → 冒烟 → CHANGELOG + package.json 版本 → 提交。
2. 改 `server.js` 必须重启 8787；改静态文件不用。
3. 写盘一律 `writeText()`（先 .bak）；路径过 `isSafePath()`；AI 写盘一律 proposal。
4. 新扫描规则进 `novel-canvas.config.json`，不硬编码。
5. 新批处理/清理逻辑**不进写请求关键路径**（pruneBackups 挂死教训）。
6. 显隐用 `.on` 类不用 `hidden`；跳转一律 `focusNode`；弹窗覆盖注意 `.modal.analysisModal` 双类特异性。
7. 诚实报告：「已构建」与「已运行验证」分开写；测试没过就说没过。
