## 一、缺陷 1：统计口径不一致 —— ✅ 确认存在，且比交接卡描述的更严重

交接卡说"字数、卷归属、伏笔状态在不同模块用了不同算法"。逐行比对后的精确结论：

### 1.1 卷归属：两套算法 + 一处死代码误导（实锤）

**服务端** `server.js` `buildBookStats()` L1907–1911：

```js
// 按文件路径倒数第二段取卷名（与前端 volumeKeyOf 一致）   ← 这句注释是错的
const parts = String(c.file || '').split(/[\\/]/);
const vol = parts.length > 1 ? parts[parts.length - 2] : '未分卷';
```

- **无条件**取父目录名；兜底词 `'未分卷'`。

**前端** `app.js` 存在**两个同名函数** `volumeKeyOf`：

| 位置 | 逻辑 | 状态 |
|---|---|---|
| L95–99 | 无条件取倒数第二段，兜底 `'未分卷'` | **死代码**（JS 函数声明后者覆盖前者，全局生效的是 L317） |
| L317–327 | 父目录**必须含「卷」字**才采用；否则从 `标题+文件名` 正则提取「第X卷 / XX卷」；再兜底 `'全局'` | **实际生效** |

即：**服务端注释自称"与前端一致"，但它对齐的是被覆盖的死代码 L95，不是真实生效的 L317。**

**必然分叉的场景**（统计弹窗的数字用服务端口径，下钻明细 `app.js` L5603/5618/5633 用前端口径过滤）：

| 场景 | 服务端卷名 | 前端卷名 | 结果 |
|---|---|---|---|
| 章节目录名不含「卷」（如 `正文/`、`chapters/`、`冰霜之地/`） | `正文` / `chapters` / `冰霜之地` | 标题正则命中→`第X卷`，否则 `'全局'` | 点开该卷下钻 → **过滤 0 行** |
| 章节直接在项目根（无子目录） | `未分卷` | 标题正则命中→`第X卷`，否则 `'全局'` | 下钻永远 0 行 |
| 目录含「卷」（如 `第一卷/`、`第三卷·源能回廊/`） | `第三卷·源能回廊` | `第三卷·源能回廊` | 一致（所以《列车求生》这类项目**碰巧不发作**） |

**这解释了为什么缺陷平时没暴露**：用户现有项目的卷目录都带「卷」字，两套算法恰好同解。
一旦新建不带「卷」字的目录（如按场景命名的卷目录），用户立刻看到"统计有这卷、点进去是空的"。

### 1.2 字数：含空白 vs 不含空白（实锤，交接卡未指明具体差异）

| 模块 | 位置 | 算法 |
|---|---|---|
| 服务端 `buildBookStats`（统计弹窗「总字数」「各卷字数」） | `server.js` L1904、L1914 | `(content \|\| '').length` —— **含换行/空格** |
| 看板「章节总字数」及逐章字数列 | `app.js` L917 | `content.replace(/\s+/g,'').length` —— **不含空白** |
| 编辑器底部计数 | `app.js` L1412 | 不含空白（文案明示「字数（不含空白）」） |

后果：**同一本书同时显示两个不同的"总字数"**，统计弹窗永远比看板/编辑器大（差值=全书的换行+空格数，长篇可差数千）。用户对照时直接观感是"软件坏了"。

### 1.3 伏笔状态：交接卡的怀疑**不成立**，但有相邻的定义分歧

- 服务端 `foreshadowStatusOf`（`server.js` L1188–1192）与前端 `parseForeshadowStatus`（`canvas_upgrade.js` L275–279）**算法完全相同**（`split('|')` 取第 5 列）。✅ 这条口径是统一的。
- **但**：统计弹窗 `planted = total − recovered`（server.js L1933，把「未标记/待回收/断线」等一切非"已回收"都算"未回收"），而看板「未回收伏笔」只算 `'已埋' + '计划回收'`（`app.js` L902）。两处"未回收"数字**定义不同必然不等**。

## 二、缺陷 2：`fmCache` 无失效机制 —— ✅ 确认存在，证据完整

`server.js`：

- L709–717 `fileFrontMatter()`：缓存键 = `root + '|' + file`，**无 mtime/内容校验**，写入后永久有效。
- L718 `invalidateFmCache(root)`：**定义存在，但全项目 0 处调用**（grep 仅命中定义行本身）。
- L3393 `fmCache.clear()`：**唯一**的失效点，挂在 `POST /api/config`（保存项目扫描配置）里。

**所有写盘路径均无失效动作**（逐行核对）：

| 写盘入口 | 位置 | 缓存失效 |
|---|---|---|
| `/api/file/save`（编辑器手动/自动保存） | L3515–3528 | ❌ 无 |
| `/api/apply_proposal`（edit / create / delete / file_edit 四分支） | L2707–2760 | ❌ 无 |
| `/api/file/delete` / `rename` / `create` | L3531+ | ❌ 无 |

消费方：L819 `buildNodes` 管线内 `fmByFile.set(n.file, fileFrontMatter(n.file, root))` —— front matter 是**层 2 识别**（type/label/chapter/level/lane）的数据源。

**可复现后果**：在编辑器里改某文件的 front matter（比如把 `lane: 感情线` 改成 `lane: 势力线`）→ 保存成功 → 重新加载节点 → **画布仍按旧 lane 渲染**，直到「保存项目配置」或重启 8787 服务。这正是"实时监控"目标的直接反例。

**修复成本极低**（两条路任选，阶段方案见 02 文档）：
a) `fileFrontMatter` 缓存值带 `mtimeMs`，读时比对；
b) 在 `writeText()`（所有写盘的必经收口）里单行调用失效。

## 三、新增发现（交接卡/任务书均未提及）

### 3.1 `volumeKeyOf` 重复定义是独立技术债
`app.js` L95 与 L317 两个同名函数共存，L95 永远不可达，还误导了 server.js 的注释作者。应删除 L95 并把口径收敛为**一处实现、前后端共用**（前端直接用服务端下发的 `volume` 字段，不再自己算）。

### 3.2 「引入统一 toast」的真实剩余工作量
- toast 已存在：`showToast(text, type)`（info/success/error），`app.js`/`file_editor.js` 大量调用点；配套 `#confirmModal` + `confirmDialog()` 也已存在（HANDOVER 弹窗统一会话记录，index.html 26 处 + file_editor.js 10 处 alert/confirm 当时已替换）。
- **残留**：仍有一批原生弹窗未收敛（实测 grep）：
  - `prompt()`：`app.js` L3165/L3181/L4054、`file_editor.js` L726/L766/L799、`canvas_upgrade.js` L281/L290 —— prompt 无 toast 对应物，**需要新增"输入弹窗"组件**才能收敛；
  - `alert()`：`app.js` L5400、`canvas_upgrade.js` L285/L294 等少量残留。
- 即方向一这条的真实表述是：**"补输入弹窗组件 + 收尾约 10 处原生弹窗"**，不是"从零引入 toast"。

### 3.3 小地图硬编码色（任务书引 HANDOVER L66，已坐实）
`canvas_upgrade.js` L48 `ctx.fillStyle = '#f4f6fb'`（背景）、L62 `ctx.strokeStyle='#b45309'`（视口框）——深色主题下确实未适配。注意这是 **canvas 2D 上下文**，不能用 CSS 变量，需要读 `getComputedStyle` 取 token 值。
